# LLM Prompt for Meal Plan Generation

## Weekly plan generation

The planner sends two messages to the LLM:

- **System message:** the prompt generated by `build_plan_prompt()`.
- **User message:** `Generate weekly meal plan`.

The prompt is built in
[`src/meal_planner/llm/prompts.py`](../src/meal_planner/llm/prompts.py)
and sent from
[`src/meal_planner/planner_handler.py`](../src/meal_planner/planner_handler.py).

The system prompt has this structure:

```text
You are an expert nutritionist and meal planner.
Generate a 7-day meal plan based on the profile below.

=== REQUIREMENTS ===
Week Start Date: {week_start}
Include at most four meals per day.
Profile & Constraints:
{family name, people count, family members, calorie targets,
 optional protein/fibre targets in grams/day ("not set" when absent),
 allergies, dietary preferences, restrictions, goals}

=== REQUEST-SPECIFIC PREFERENCE (HIGH PRIORITY) ===
{user's preference, or "No additional preference."}

Use this request preference when compatible with the permanent
profile constraints below. Allergies, restrictions, calorie
targets, and safety requirements always take precedence.

=== INTERPRETED PREFERENCE RULES (EXACT COMPLIANCE) ===
{measurable rules extracted from the preference}

Treat each exact_count as an exact weekly count. Do not omit,
weaken, or reinterpret any listed rule. Permanent profile
constraints remain higher priority.

=== GENERATED PLAN CONTRACT ===
Include exactly one breakfast, one lunch, and one dinner on each
of the 7 days. Snack is optional, and do not add other meal types.
Every present meal must include at least one non-empty ingredient
item and positive est_calories.

Recent Meal History (avoid repeating):
{last 14 days of meal history}

Previous Plan Feedback:
{cooked, skipped, and swapped meals from the previous plan}

=== OUTPUT JSON SCHEMA ===
Return strictly valid JSON matching this schema:
{
  "week_start_date": "YYYY-MM-DD",
  "status": "draft",
  "days": [
    {
      "day": 1,
      "meals": [
        {
          "meal_type": "breakfast|lunch|dinner|snack",
          "name": "Meal Name",
          "ingredients": [
            {"item": "Ingredient", "amount": "Quantity"}
          ],
          "est_calories": 500,
          "outcome": "unreported"
        }
      ]
    }
  ]
}
```

The real prompt replaces the placeholders with the user's profile,
requested week, preference, interpreted requirements, meal history, and
previous-plan feedback. The complete schema requires all seven days.

Each supplied per-member calorie, protein, and fibre target is included in the
rendered profile context. For example:

```text
Family member targets:
- Alex: 2000 kcal/day; protein 120 g/day; fibre 30 g/day
- Sam: 1800 kcal/day; protein not set; fibre not set
```

The generation requirements use these values to guide meal choices and
portions. Protein and fibre targets are optional, and the prompt never
invents values for targets that are not set. Dietary constraints and safety
requirements remain higher priority.

This is prompt-guided, best-effort adjustment. The plan output keeps its
existing calorie estimate field; the application does not calculate nutrient
totals, validate calorie, protein, or fibre compliance, detect missed targets,
or automatically repair a plan for missing target compliance.

## Preference interpretation

When the user provides a preference, a separate LLM call first converts it
into measurable rules. For example, “eggs three times for breakfast” becomes
a requirement with:

```json
{
  "foods_any_of": ["eggs"],
  "meal_type": "breakfast",
  "exact_count": 3
}
```

This prompt is built by `build_preference_interpretation_prompt()` in
[`src/meal_planner/llm/prompts.py`](../src/meal_planner/llm/prompts.py).
The user's preference is sent as the user message for that call.

## Repair generation

If the first plan is invalid, the planner schedules one repair attempt. The
same generation prompt receives an additional section:

```text
=== BOUNDED REPAIR FEEDBACK ===
{validation errors, maximum 800 characters}

Correct the feedback while preserving all permanent profile constraints
and the exact rules above.
```

The application parses and validates the returned JSON after generation; it
does not trust the model output solely because the prompt requests valid JSON.

## LLM request settings

The request uses:

- Model: `PLANNER_LLM_MODEL` (default: `gpt-5.6-luna`)
- Reasoning effort: `PLANNER_LLM_REASONING_EFFORT` (default: `high`)
- Response format: `{"type": "json_object"}`

The messages are sent as:

```python
[
    {"role": "system", "content": plan_prompt},
    {"role": "user", "content": "Generate weekly meal plan"},
]
```
